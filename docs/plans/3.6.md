# Task 3.6 — SDKs and docs site

Covers: F-14 (Could), and the developer-facing half of F-01, F-02, F-03.
Depends on: 1.14 (`/openapi.json` served from the binary).

## Intent

A developer integrates in under 15 minutes (§4 of the PRD). That is the whole bar, and
it decides every choice below.

## Two decisions, taken without an ADR

**Thin clients over generated types, not generated clients.** `openapi-generator` emits
thousands of lines nobody reviews, and still cannot do the two things that make this API
worth wrapping: chunked streaming and the WebSocket. So the *types* are generated from
`docs/api/openapi.yaml` — `openapi-typescript` for JS, `datamodel-code-generator` for
Python — and the transport is hand-written and small enough to read. Generation runs in
`make generate`, so the contract-drift job fails if an SDK's types fall behind the API.

**The docs site is a public route in the console, not a new service.** A separate static
site would be new infrastructure needing its own ADR and its own image, to render a file
the gateway already serves at `/openapi.json`. The console is already deployed, already
has the design system, and already talks to the same API. `/docs` is public — a developer
reading the quickstart does not have a key yet.

## Deliberately out of scope

- **Publishing to npm and PyPI.** That is outward-facing and irreversible per version; it
  is the owner's call, not a step in a task. Both packages install from the repo.
- Admin endpoints. They are operator tools behind an IP allowlist, not something a
  tenant's SDK should make easy to call.
- A WebSocket client in Python. The JS one exists because browsers and Node have the
  transport built in; Python would need a new dependency for a path `stream()` already
  covers over plain HTTP.
