# Task 3.5 — Minimal console

Covers: F-12, and the browser half of US-13, US-16, US-17.
Depends on: 2.6 (key management), 2.7 (usage report). Decided by ADR-012.

## Intent

A tenant can paste a key, see what they have used, and create or revoke keys. Nothing
else. The console is a client of the public API and holds no secret of its own.

## Design direction

The anti-template rule needs a decision, not a default, so:

**Technical editorial.** A document, not a dashboard. Paper-white ground, near-black ink,
a single lacquer red drawn from Vietnamese sơn mài as the only accent, and one muted
support tone. Hierarchy comes from scale contrast and rhythm, not from boxes: the usage
figure is set large and typographically, the way a printed report leads with its number.

- Type: a grotesque for text, a monospace for every identifier, key prefix and figure —
  a developer console is mostly numbers and identifiers, so the mono is structural rather
  than decorative.
- The chart is drawn as inline SVG against the same type scale and the accent colour. No
  chart library: its defaults are exactly the template look this rule exists to prevent,
  and a daily bar series is a `path` and a loop.
- Motion is limited to state changes that need explaining — a key being revealed once, a
  row leaving on revoke.
- Light only. This is a report you read, and dark mode here would be a default, not a
  decision.

## Deliberately out of scope

- A jobs screen. The task row asks for key login, usage and key management; jobs have an
  API and no story asking for them in the browser. It is a screen to add when someone
  asks, not a screen to guess at.
- Any login that is not the API key. There are no console accounts, so a password flow
  would mean inventing an identity system the product does not have.
- Dark mode, and a component library. Both are defaults rather than decisions here.
