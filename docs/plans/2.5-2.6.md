## Decisions

- **The signature covers `"<timestamp>.<body>"`.** Signing the body alone would let a
  captured delivery be replayed later with a fresh timestamp header, which is exactly
  what a receiver checking freshness would then accept (US-15 AC-1).
- **`VerifySignature` ships next to `Signature`.** A receiver has to reimplement this,
  and the one definition here is what the SDKs copy verbatim.
- **Delivery runs on its own goroutine, detached from the request context.** A tenant's
  slow endpoint must not hold up an orchestrator that has other jobs to finish, and the
  delivery outlives the work that triggered it.
- **4xx responses are retried too.** A receiver deploying badly for a minute should not
  lose its notification, and five attempts bound the cost either way.
- **The SSRF guard runs before *every* attempt**, not just at job creation: DNS can
  change in the minutes between the two, and a name that was public then may point
  inward now (US-15 AC-3).
- **An empty signing secret fails the boot.** A webhook signed with nothing is not
  signed, and a receiver that verifies would reject every delivery — better to find that
  at deploy time than in a customer's logs.
- **A key can never mint a more powerful key.** Requested scopes must be a subset of
  what the calling key holds, so a leaked `synth` key cannot escalate to `keys`.
- **Revoking evicts the auth cache immediately.** US-05 allows a 60 s lookup cache; a
  revocation that waits it out is a minute of access after the operator believed it was
  gone (US-17, T-18).
- **Revoking a key you are currently using is allowed.** An operator whose key leaked
  holds no other credential, and forcing them to create a replacement first would leave
  the leaked key live for longer.
- **Another tenant's key, a missing key and an already-revoked key give the same
  answer.** Which ids exist is not something we disclose.

## Layering fix

The webhook dispatcher first landed inside `internal/jobs`, and `depguard` rejected it:
a use case may not import `net/http`. It is an outbound adapter, so it now lives in
`internal/webhook` and satisfies the `jobs.Notifier` port. The rule caught a real
misplacement rather than a technicality.

## Verified

```
make lint              0 issues (incl. depguard layering)
make test              gateway 233 tests, worker 53
live stack, key lifecycle:
  POST /v1/keys                       201, scopes [synth], secret returned once
  new key → GET /v1/voices            200
  new key → GET /v1/keys              403 forbidden_scope
  DELETE /v1/keys/{id}                204
  revoked key → GET /v1/voices        401, immediately                        (T-18)
```

**Webhook delivery is verified by unit tests against a real HTTP server**, not against
the live stack: in development every reachable receiver is on a private address, and the
SSRF guard refuses those — correctly. Weakening the guard to demonstrate the happy path
would have removed the property the guard exists for.
